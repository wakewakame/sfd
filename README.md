# SFD (Similar File Detector)

膨大にある画像・動画ファイルの中から類似のファイルを検出するためのツールです。

# 使い方

## sfd hash

```sh
$ sfd hash ./dir/ hash.json
```

./dir 以下の全ての画像・動画ファイルを再帰的に探索し、その知覚ハッシュ等を hash.json に出力する。

hash.json は 1 行 1 JSON (JSONL) で、1 行目をヘッダとする。

```sh
$ cat hash.json
{"v":1,"root":"./dir"}
{"path":"1.jpg","bytes":100,"mtime":"2026-09-02T01:23:45Z","sha256":"xxx","width":4032,"height":3024,"pdq":[{"t":0.0,"hash":"xxx","quality":100}]}
{"path":"2.png","bytes":200,"mtime":"2026-08-31T12:00:00Z","sha256":"xxx","width":1024,"height":768,"pdq":[{"t":0.0,"hash":"xxx","quality":95}]}
{"path":"3.mp4","bytes":300,"mtime":"2026-07-01T09:30:00Z","sha256":"xxx","width":1920,"height":1080,"duration":123.4,"pdq":[{"t":30.8,"hash":"xxx","quality":100},{"t":61.7,"hash":"xxx","quality":98},{"t":92.5,"hash":"xxx","quality":97}]}
{"path":"4.jpg","bytes":50,"mtime":"2026-06-15T18:00:00Z","sha256":"xxx","error":"ffmpeg が失敗しました: ..."}
```

- `path` はヘッダの `root` からの相対パス。ディレクトリごと移動しても hash.json が使える
- **画像も「1 フレームの動画」として同じ形で持つ**。画像と動画で形が変わらないので、
  比較する側は常に「ハッシュの集合どうしの比較」として書ける。画像の `t` は 0
- `duration` を持つかどうかが画像と動画の区別になる
- `pdq` はどのフレームかを位置ではなく `t` (秒) で持つ。
  将来サンプリング方法を変えても、古い hash.json が静かに誤解釈されない
- `width` / `height` / `duration` / `quality` は、どのファイルを残すか決めるときの判断材料になる。
  計算時にはすでに手元にある値なので記録コストはゼロだが、後から足すと全ファイルの再スキャンになる
- `error` を持つ行は処理に失敗したもの。中断せず記録して次に進む

## sfd find

```sh
$ sfd find hash.json find.json
```

hash.json を元に、似ているファイルをまとめて find.json に出力する。

先頭のファイルから順に、しきい値以内にある他のファイルを列挙する。一度どこかのグループに現れたファイルは、以降のグループには現れない。

```sh
$ cat find.json
{"v":1,"threshold":31}
{"path":"1.jpg","bytes":100,"width":4032,"height":3024,"similar":[{"path":"1-copy.jpg","distance":0,"identical":true,"bytes":100,"width":4032,"height":3024},{"path":"1-small.png","distance":12,"bytes":50,"width":1024,"height":768}]}
```

- 似たファイルが 1 つもないものは出力しない
- 解像度やサイズをファイルごとに開き直さずに比較できるよう、判断材料は find.json 側にも持たせる
- `identical` は sha256 が一致するもの。見た目を比べるまでもなく片方を消してよい

# メモ

- 知覚ハッシュの計算には [pdq](https://github.com/facebook/ThreatExchange/tree/main/pdq) を用いる
    - リファレンス実装の逐語移植を [pdq/](pdq) に置いた。公式の回帰テストベクタとビット単位で一致する
    - 単体で使える `phashsum` コマンドも同梱している
- 動画は動画を 4 分割して 1/4, 2/4, 3/4 地点のフレームに対してそれぞれ知覚ハッシュを計算する
    - シークは `-ss` を `-i` **より前**に置く。速いうえにフレーム精度も出る
    - `-noaccurate_seek` を付けてはいけない。キーフレーム基準に戻ってしまう
    - ここは再現性に直結する。取れるフレームがキーフレーム配置に依存すると、
      同じ動画の再エンコード版から別のフレームが取れて知覚ハッシュが一致しなくなる
    - ffmpeg 2.1 (2013-10) より前は `-i` の前の `-ss` がキーフレームにスナップしたため、
      正確に取るには `-i` の後ろに置く必要があった。当時の情報が今も多く残っているが、
      現在は「キーフレームまで飛んでから目的の時刻まで復号して捨てる」ので両立する
    - 実測 (ffmpeg 9.0.1): キーフレームが 0 と 5.0 秒にしかない 10fps の動画で 2.5 秒を
      要求したところ、`-ss` を前に置くと 25 フレーム目ちょうどが返った。
      `-noaccurate_seek` を付けると 23 フレーム目になった
    - `-ss` を `-i` の後ろに置くと先頭から復号するため常に正確だが、10 分の動画の
      終盤で約 10 倍遅い (0.03s に対し 0.32s)
- 画像や動画のデコードには ffmpeg を用いる
    - 中間ファイルは作らず、ffmpeg の出力を PAM (P7) 形式でパイプから受け取る
    - PAM はヘッダに寸法とチャンネル数を持つので ffprobe を別に呼ばずに済む
    - 2400 万画素の画像だと中間 png は 36MB になり、書き出しと読み直しだけで数百 ms を無駄にする
    - iPhone の HEIC はタイルが数百のストリームに見えるため、`-map` と `-vf` を使ってはいけない
- 知覚ハッシュの計算前に 512x512 へ縮小する (`pdq::preprocess::reference_downsample`)
    - リファレンス CLI と同じ前処理。公式の期待値と揃う
    - 縮小しないと 2400 万画素で 1 枚 363ms かかる。縮小すれば 3.2ms
- sha256 の計算には [sha2](https://crates.io/crates/sha2) crate を用いる
    - sha256 が既出のファイルは、知覚ハッシュを計算せず使い回す。
      デコードは 1 枚 470ms かかるのに対し sha256 は 34MB で 17ms なので、完全重複が多いほど効く
- hash.json は 1 行 1 JSON (JSONL) とする
    - エラーが起きても中断せず `{"path":..., "error":...}` の行として残す
    - 中断しても再開できるよう、既に書かれているパスは読み飛ばす
    - 強制終了で末尾行が途中まで書かれている可能性があるので、パースできない末尾行は捨てる
    - 形式を変えたときに古いファイルを検出できるよう、ヘッダに `v` を持たせる
- 進捗は標準エラー出力に出す。数時間かかるので、無言だと止まっているのか分からない
- `sfd find` の走査順はパス順に固定する
    - 「似ている」は推移律を満たさない。A〜B かつ B〜C でも A〜C とは限らない
    - 先頭のファイルからの 1 ホップだけを見て、一度出たファイルを除外することでこれを回避している
    - この方式は走査順で結果が変わるので、順序を決めておかないと実行のたびに出力が変わる

# 未定

`sfd find` は以下を決めてから実装する。

- 一致とみなすハミング距離のしきい値 (PDQ 公式の推奨は 31/256)
- 動画同士の比較方法。3 ハッシュ × 3 ハッシュのうち 1 つでも近ければ一致とするか
- 画像と動画を比較するか (動画から切り出した静止画を検出したいなら必要)
- 回転・反転を同一視するか。`pdq` の dihedral を使えば実現できるが、保持するハッシュが 8 倍になる
- quality による足切りをするか (のっぺりした画像は偶然一致しやすい)
- 探索方法。数万件なら全ペア総当たりで足りる (256bit の popcount は速い)。数十万件を超えるなら BK-tree か MIH
- グループの先頭をどう選ぶか。パス順のままか、解像度が最大のものを先頭に持ってくるか
  (残す候補が先頭に来ていた方が見やすい)
